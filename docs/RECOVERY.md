# Unfinished sessions and local checkpoints

The startup recovery pane lists unarchived sessions, their project/worktree/branch/harness, last activity, captured state and checkpoint timestamp. Runtime labels are **running** (a session owned by the current daemon), **stopped** (an observed exit), or **unknown** (a formerly live record with no current PTY owner). Historical checkpoint state remains visible separately. Click a session to inspect/copy its output tail and see recovery actions.

The existing SQLite database migrates to schema 3. Each worker has at most one plain-text transcript checkpoint, capped at 16 KiB; retention is limited to seven days and 512 workers. Output/control sequences are parsed into plain text, and truncation is indicated. Checkpoints follow changed output/activity/state at most once every two seconds, with an immediate observed-exit checkpoint. This is best-effort context; a crash can lose the final two seconds, and a transcript excerpt is not an exact screen snapshot or a conversation database.

Closing/reopening the UI reconnects to the same daemon and its live PTYs. After a daemon crash, active persisted workers are marked lost and their process state is unknown. No live PTY recovery or automatic resume occurs. A live session rejects a duplicate resume. For unknown state, inspect the recorded PID and stop any surviving old process before clicking a button labeled **Verified stopped** or passing `sdk resume WORKER_ID --acknowledge-unknown`. PIDs can be reused; saved PID alone is not proof of identity or liveness.

Fresh resume starts a new process in the existing worktree. Claude, Codex, Gemini and opencode support their harness’s worktree-scoped latest/continue flags through the existing executor adapters; this is not recovery by an exact SigmaDock-owned conversation ID. Inspect the resumed harness before giving new instructions. Aider and shell have no managed conversation continuation and the pane explains that limitation. Codex continuation accepts no simultaneous prompt; use `sdk message` after startup.

**Clear saved context** deletes its row and moves the capture boundary so old in-memory output is not saved again. Later activity can create a new checkpoint. It does not clear the visible live terminal or delete worktrees. Archiving clears context and hides the session; clean worktree removal is still a separate explicit cleanup action. SQLite/WAL backups may retain old pages, so this is not secure erasure.

An already-running older daemon remains running when the app updates. New recovery methods require the new daemon; finish/stop its workers and restart it explicitly when convenient. The UI shows unavailable recovery data without terminating workers. Schema 3 is rejected by older daemons, so preserve a backup if planning a downgrade.
